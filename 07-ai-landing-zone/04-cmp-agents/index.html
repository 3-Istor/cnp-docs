    La CMP et les agents¶

    Statut : v1.0 du 2026-10-25, validée par Brian. Cette page dit comment un développeur ou un tenant active l'IA et déclare un agent dans la CMP, et ce que la CMP écrit en conséquence. Les décisions de plateforme sont dans 02-spec.md, les phases dans 03-phases.md. Les noms d'API et d'écrans sont des propositions.

    1. Ce qui existe déjà¶

    La landing zone IA s'appuie sur des mécanismes que la CMP a déjà ; elle les étend plutôt que d'en créer de nouveaux.

    Existant Où Ce que les agents en réutilisent
    Projets = groupes Keycloak du realm 3istor keycloak_service.py Le groupe project-<projet>-agents et la création des clients d'agent
    ProjectRecord (cnp.3istor.com/v1alpha1) avec spec.apps et spec.features, écrit par la GitHub App de la CMP cnp-projects/registry/projects/<projet>.yaml Un bloc spec.ai et une liste spec.agents
    Chart cnp-project-base, rendu par les ApplicationSets d'Argo CD cnp-project-base/templates/ Les ressources par agent (namespace, NetworkPolicy, quotas, Agent)
    Apps créées depuis des templates (dépôt GitHub, CI, release par tag) app-templates, infra-templates Des templates d'agent ; un agent est une app avec un dépôt et des releases
    Serveur MCP de la CMP, stake policy par niveau de projet (sandbox, demo, standard, critical) backend/app/mcp_server.py, services/agents/policy.yaml Les outils de plateforme et les règles par action
    Confirmations dans la CMP (approuver ou refuser une action demandée par un assistant) routers/agents.py, ConfirmationPanel Les approbations des actions d'agents hébergés
    Réglages assistants par projet : niveau, fenêtre autonome ProjectAgentPanel Le même panneau, étendu aux agents hébergés
    FinOps : budgets, jauges, recommandations /finops, BudgetForm, BudgetGauge Le budget en tokens et le coût par agent
    Journal d'activité, qui enregistre déjà l'assistant (via) /activity, audit.py L'agent comme auteur d'une action

    2. Ce que font les autres¶

    Les plateformes du marché convergent vers les mêmes briques que la landing zone de CNP, ce qui valide le design. Elles diffèrent surtout par l'expérience proposée.

    Plateforme Ce qu'elle propose Ce que CNP en retient
    AWS Bedrock AgentCore Runtime, Gateway (MCP, inférence avec repli de modèle, limites de débit), Identity (OAuth au nom de l'utilisateur, portail de consentement), Policy (avec Bedrock Guardrails), Memory, Observability, Evaluations (A/B, batch), Agent Registry ; outils intégrés : navigateur, interpréteur de code, recherche web La recherche web comme outil fourni par la plateforme ; un écran de consentement quand un agent agit pour un utilisateur ; les évals comme étape de publication
    Google Gemini Enterprise Agent Platform (avril 2026) Agent Registry, Agent Gateway (identité et accès), policies, télémétrie, journaux d'audit, Agent Studio (low-code) Un registre unique des agents et de leurs endpoints, consultable par tous
    Microsoft Foundry + Agent 365 Inventaire de tous les agents (y compris ceux non déclarés), identité Entra par agent, activation et désactivation, propriétaire et attestation périodique, approbation d'un admin avant publication, tableaux d'activité Un propriétaire par agent, un bouton de coupure, une revue périodique des agents à fort impact
    OpenAI AgentKit Agent Builder (canevas visuel, templates, aperçu, versions, nœuds de guardrails, évals intégrées), Connector Registry, ChatKit (interface de chat à intégrer) Les templates, l'aperçu avant publication, les versions. Agent Builder et Evals s'arrêtent le 30 novembre 2026 au profit du SDK : pas d'éditeur visuel de workflow dans la CMP
    kagent (déjà retenu, D8) Interface : liste des agents avec chat, modèles, bibliothèque d'outils, serveurs MCP Le chat de test directement sur la page de l'agent

    Ce qu'on ne copie pas. Pas d'éditeur visuel de workflow : le code de l'agent vit dans son dépôt (LangGraph, ADK…), la CMP ne gère que sa déclaration. Pas de mémoire longue gérée par la plateforme au départ : le RAG par projet suffit pour la démo. Pas de paiements.

    3. Parcours¶

    Chaque parcours indique sa phase (spec §6).

    # Parcours Qui Phase
    C1 Activer l'IA sur un projet : niveau de données (Cloud ou Local), budget du projet, modèles autorisés admin du projet 1
    C2 Donner l'accès aux modèles à une app existante (par exemple le clone de Twitter) admin du projet 1
    C3 Créer un agent depuis un template membre du projet 2
    C4 Choisir ses outils dans le registre et voir le profil de risque calculé membre du projet 2
    C5 Tester l'agent dans un chat, avec le détail de chaque étape membre du projet 2
    C6 Publier une version (tag de release, évals en CI, approbation si le projet est critical) membre du projet 2
    C7 Suivre l'agent : tokens, coût, erreurs, refus, traces membre du projet 1 (app), 2 (agent)
    C8 Approuver ou refuser une action en attente admin du projet 2
    C9 Suspendre un agent en un clic, puis le réactiver admin du projet, admin plateforme 2
    C10 Supprimer un agent admin du projet 2
    C11 Inventaire global des agents, registre des serveurs MCP, état des modèles admin plateforme 2
    C12 Revue périodique : le propriétaire confirme qu'un agent sert encore et que ses droits sont justes propriétaire 3

    4. Où l'IA apparaît dans la CMP¶

    La barre latérale de la CMP contient aujourd'hui Home, FinOps, Sécurité, Activité, Alertes, Assistants IA et Docs, puis la liste des projets. Une page de projet a les onglets Apps, Membres, Sécurité, FinOps, Activité, Alertes et Assistants.

    Emplacement Changement Phase
    Onglet « Assistants » d'un projet Devient l'onglet « IA », en trois sections : Accès aux modèles, Agents hébergés, Assistants connectés (le panneau actuel, inchangé). Tout ce qui touche à l'IA d'un projet est au même endroit. 1 (sans la section Agents), 2
    Barre latérale Nouvelle entrée « Agents » (/agents) : les agents de mes projets ; pour un admin plateforme, trois onglets en plus : Tous les agents, Outils MCP, Modèles. L'entrée « Assistants IA » (/connect-ai) reste la page pour connecter un assistant externe. 2
    FinOps Catégorie « IA » et dimension « agent » (06-finops-ia.md) selon le plan FinOps
    Page d'une app Badge « Accès IA » et lien vers la section Accès aux modèles du projet 1
    Activité Filtre « via un agent » 2

    Les maquettes de ces écrans sont sur le canevas CMP · Landing zone IA · Maquettes (privé, à partager depuis claude.ai) : onglet IA d'un projet, accès IA d'une app, création d'un agent à l'étape Risque, page d'un agent avec chat de test, inventaire des agents, FinOps filtré sur l'IA. Elles sont la référence visuelle ; ce document reste la référence fonctionnelle.

    5. Écrans¶

    Projet, onglet « IA »¶

    • Carte « Niveau de données ». Cloud ou Local, avec une phrase sur ce que ça implique (« Local : vos données ne quittent pas le homelab ; les réponses sont plus lentes »). Un projet critical est forcé en Local.
    • Carte « Budget ». Jauge des tokens consommés aujourd'hui, coût au prix public de Gemini, seuil d'alerte. Reprend BudgetGauge et BudgetForm.
    • Carte « Modèles ». Modèles autorisés pour le projet, et l'état de chaque backend (Gemini : quota restant ; serveur GPU : en ligne ou « service indisponible »).
    • Liste « Agents et apps avec accès IA ». Nom, type (agent ou app), version, statut, isolation, tokens du jour, dernière activité.
    • Boutons. « Créer un agent » ; « Donner l'accès IA à une app ».

    Assistant de création d'un agent¶

    Sur le modèle du DeploymentStepper des apps, en six étapes :

    1. Template. Agent déclaratif vide (consignes, modèle, outils, sans code), agent de questions sur une doc (RAG), agent de diagnostic de déploiement (UC3), agent de revue de PR (UC11). Un agent déclaratif n'a pas de dépôt de code : la CMP écrit son CR Agent. Un agent BYO (LangGraph) a un dépôt avec le code, le Dockerfile et deploy/.
    2. Identité. Nom, description, propriétaire (par défaut le créateur).
    3. Modèle. Choix parmi les modèles autorisés du projet, et plafond d'étapes par tâche.
    4. Outils. Liste du registre, chaque outil avec ses badges de risque (« lit du contenu non fiable », « écrit », « sort vers Internet », « exécute du code »). Exemples : outils de la CMP, GitHub, recherche web, recherche dans la doc du projet, génération d'image.
    5. Risque. Quatre questions, préremplies à partir des outils choisis : exécute-t-il du code ? lit-il du contenu non fiable ? accède-t-il à des données privées ? envoie-t-il vers l'extérieur ? La CMP affiche le niveau d'isolation qui en découle et le verdict de la Rule of Two. Trois risques cumulés bloquent la création, avec la proposition de couper en deux agents.
    6. Résumé. La carte des capacités de l'agent (ci-dessous), ce qui va être créé (dépôt, client, namespace, budget), puis « Créer ». Dans un projet critical, la création passe par une pull request ou une approbation, selon la stake policy.

    Page d'un agent¶

    • En-tête. Nom, statut (actif, suspendu, en erreur), version, badges d'isolation et de risque, propriétaire.
    • Boutons. « Tester », « Publier une version », « Suspendre » ou « Réactiver », « Paramètres », « Supprimer ».
    • Onglet Aperçu. Tokens du jour face au budget, coût, taux d'erreur, nombre de refus (budget, policy, guardrails).
    • Onglet Tester. Un chat qui passe par la gateway, comme en production, avec le jeton de l'utilisateur ; à côté, le détail de chaque étape : appels de modèle, appels d'outils, décisions des guardrails, tokens. Les tokens consommés comptent dans le budget de l'agent.
    • Onglet Traces. Les dernières tâches, avec un lien vers la trace dans Grafana.
    • Onglet Capacités. Une carte en lecture seule, pas un éditeur de workflow : ce que l'agent lit, ce qu'il peut faire, où il peut envoyer, avec les outils correspondants. En haut, les trois risques de la Rule of Two (données privées, contenu non fiable, sortie vers l'extérieur), allumés ou éteints, et le verdict « 2 sur 3 au plus ». Quand une tâche est coupée en deux agents, la carte montre la chaîne : l'agent lecteur, le résumé structuré qu'il transmet en A2A, puis l'agent qui agit, chacun avec ses risques allumés. La même carte apparaît au résumé de la création. Elle se calcule depuis la déclaration de l'agent (ses outils et leurs badges), donc elle reste juste sans effort de l'utilisateur.
    • Onglet Outils et accès. Outils autorisés ; qui peut appeler l'agent (membres, groupes, autres agents en A2A) ; son Agent Card.
    • Onglet Évals. Résultat du dernier passage de promptfoo, par version.
    • Onglet Journal. Actions de l'agent, demandes d'approbation, changements de réglages.

    Administration de la plateforme¶

    • Agents. Inventaire de tous les agents : projet, propriétaire, isolation, statut, dernière activité ; filtre et bouton de coupure.
    • Outils MCP. Registre des serveurs : provenance, outils exposés, risque ; approuver ou retirer un serveur. L'approbation est une PR sur le registre dans Git.
    • Modèles. Backends, quota Gemini restant, état du serveur GPU, table des prix.

    Écrans existants à étendre¶

    • FinOps. Tokens et coût par projet et par agent.
    • Journal d'activité. Les actions d'un agent hébergé, avec via: agent-<projet>-<nom>.
    • Confirmations. Les demandes des agents hébergés, au même endroit que celles des assistants.

    6. Ce que la CMP écrit¶

    La CMP n'applique rien directement sur le cluster : elle écrit dans Git et dans Keycloak, et Argo CD fait le reste, comme pour les apps.

    Objet Où Phase
    Bloc spec.ai : niveau de données, budget du projet, modèles autorisés ProjectRecord dans cnp-projects (schéma schema.json et validateur à étendre) 1
    Liste spec.agents[] : nom, dépôt, template, isolation, outils, budget par jour, plafond d'étapes, appelants autorisés, statut ProjectRecord 2
    Client Keycloak agent-<projet>-<nom> dans le groupe project-<projet>-agents (ou un client pour une app, en phase 1) Keycloak, realm 3istor, par l'API d'administration 1
    Secret client (phase 1 seulement) Vault kvv2/projects/<projet>/agents/<nom> 1
    Namespace, ServiceAccount, NetworkPolicy, ResourceQuota, LimitRange de l'agent Rendus par cnp-project-base à partir de spec.agents[] 2
    CR Agent de kagent et son ModelConfig Rendus par cnp-project-base 2
    Politique de la gateway pour l'agent : budget, outils autorisés, appelants A2A Namespace ai-gateway, rendue par le chart cnp-ai-policies du dépôt K3s à partir du ProjectRecord (spec D22) 1 (budget), 2 (outils, A2A)
    Dépôt du code de l'agent, à partir d'un template GitHub, template dans app-templates 2

    Suspendre (C9) : retirer le client Keycloak du groupe et passer status: suspended dans le ProjectRecord, ce qui ramène l'agent à zéro réplica. Les jetons déjà émis expirent en 5 minutes au plus.

    7. API de la CMP¶

    Routes proposées, sur le modèle des API existantes (/api/projects/...) :

    Méthode et route Rôle Phase
    GET, PUT /api/projects/{projet}/ai Lire ou changer le niveau de données, le budget et les modèles du projet 1
    POST /api/projects/{projet}/ai/apps/{app} Donner l'accès IA à une app (client Keycloak app-<projet>-<app>, secret dans Vault, URL de la gateway dans son values.yaml) 1
    GET, POST /api/projects/{projet}/agents Lister, créer un agent 2
    GET, PATCH, DELETE /api/projects/{projet}/agents/{agent} Lire, modifier, supprimer 2
    POST /api/projects/{projet}/agents/{agent}/suspend et /resume Couper, réactiver 2
    POST /api/projects/{projet}/agents/{agent}/test Chat de test, par la gateway, avec le jeton de l'utilisateur 2
    GET /api/projects/{projet}/agents/{agent}/usage Tokens, coût, erreurs, refus 1 (app), 2
    GET /api/admin/agents Inventaire global 2
    GET, POST /api/admin/mcp-servers Registre des serveurs MCP 2
    GET /api/ai/backends État des backends de modèles 1

    Contrats des routes de la phase 1. Toutes exigent un jeton d'utilisateur ; PUT et POST exigent le rôle admin du projet.

    // GET /api/projects/{projet}/ai → 200
{
  "data_level": "cloud",            // "cloud" | "local"
  "daily_token_budget": 200000,     // projet : alerte seulement (D21)
  "models": ["gemini-2.5-flash"],   // modèles autorisés ; noms exacts fixés en T1.1
  "apps": [{"app": "twitter-clone", "enabled": true, "daily_token_budget": 50000}]
}

// PUT /api/projects/{projet}/ai  (même corps, sans "apps") → 200, ou 409 si le projet est critical et data_level = "cloud"

// POST /api/projects/{projet}/ai/apps/{app}  {"enabled": true, "daily_token_budget": 50000} → 201
{"client_id": "app-<projet>-<app>", "gateway_url": "http://<service de la gateway>:8080", "secret_ref": "kvv2/projects/<projet>/apps/<app>/ai-oidc"}

// GET /api/projects/{projet}/ai/usage?period=1d|7d|30d → 200
{"items": [{"azp": "app-<projet>-<app>", "tokens_in": 12034, "tokens_out": 3400, "requests": 41, "refused": 2, "budget": 50000, "cost_eur": 0.02}]}

// GET /api/ai/backends → 200
{"items": [{"name": "gemini-1", "kind": "gemini", "status": "ok", "quota_left_pct": 62}, {"name": "gpu-server", "kind": "gpu", "status": "unavailable"}]}

    Données. En phase 1, la CMP n'ajoute aucune table : le ProjectRecord est la source, l'usage vient de VictoriaMetrics. En phase 2, une table miroir agents (comme le miroir du placement des projets) accélère les listes ; Git reste la source.

    Les assistants (claude.ai, ChatGPT…) pourront créer et gérer des agents par de nouveaux outils du serveur MCP de la CMP, soumis à la stake policy (nouvelles actions agent.create, agent.publish, agent.suspend).

    8. Depuis Claude Code et en YAML¶

    Tout ce que la CMP fait par ses écrans se fait aussi depuis un assistant (Claude Code avec le plugin cnp-agent-kit, claude.ai, ChatGPT…) et se lit dans des fichiers YAML versionnés. Un développeur peut donc tout mettre en place en parlant à son assistant, sans ouvrir la CMP.

    Deux niveaux de configuration¶

    Niveau Fichier Qui l'écrit Ce qu'il contient
    Droits et plafonds du projet ProjectRecord dans cnp-projects (spec.ai, spec.agents[]) La CMP, par sa GitHub App, depuis l'écran ou un outil MCP ; jamais le tenant directement Niveau de données, modèles autorisés, budgets maximum, agents déclarés avec leurs outils, leur isolation et leurs risques
    Réglages de l'app ou de l'agent deploy/values-*.yaml du dépôt de l'app, comme les blocs secrets, db et migrations actuels Le développeur ou son assistant, par commit ou PR Le modèle utilisé parmi ceux autorisés, son budget dans la limite du projet, les consignes et les outils d'un agent déclaratif

    Le niveau du dessous ne peut jamais dépasser celui du dessus. Les règles de la gateway sont générées depuis le ProjectRecord (spec D22), pas depuis les values du tenant : un outil ou un budget demandé dans values.yaml sans droit dans le ProjectRecord est simplement refusé à la gateway (403 ou 429), et le validateur de la CI le signale avant.

    Exemple : une app qui appelle un modèle¶

    # deploy/values-backend.yaml
ai:
  enabled: true
  model: default            # un modèle parmi spec.ai.models du projet
  dailyTokenBudget: 50000   # au plus le plafond de l'app dans le ProjectRecord

    Le chart générique en déduit les variables AI_GATEWAY_URL, AI_MODEL et AI_CLIENT_ID, et le secret client par le même mécanisme Vault que le bloc secrets.

    Exemple : un agent déclaratif¶

    # deploy/values-agent.yaml
agent:
  type: declarative
  instructions: |
    Tu diagnostiques les déploiements en échec du projet. Tu lis l'état, les événements
    et les logs, tu expliques la cause, et tu proposes une PR de correction.
  model: default
  tools: [cmp__get_app, cmp__get_app_logs]   # parmi les outils accordés dans spec.agents[]
  maxSteps: 10

    Le chart générique rend le CR Agent de kagent (type Declarative) et son ModelConfig pointé sur la gateway. Un agent BYO ajoute image: et son code dans le dépôt.

    Outils MCP de la CMP pour l'IA¶

    Ils s'ajoutent aux outils actuels (whoami, create_app, push_files, cut_release…) et passent par la même stake policy :

    Outil Ce qu'il fait Action de la stake policy Phase
    get_project_ai Lire niveau de données, modèles, budgets, apps avec accès IA, état des backends read 1
    set_project_ai Changer niveau de données, modèles autorisés, budgets du projet ai.configure (nouvelle) 1
    enable_app_ai Donner l'accès IA à une app : client Keycloak, plafond dans le ProjectRecord, bloc ai dans ses values ai.configure 1
    get_ai_usage Tokens, coût au prix public, refus, par app ou agent read 1
    create_agent Déclarer un agent : spec.agents[], client, values de l'agent ; refuse trois risques cumulés agent.create (nouvelle) 2
    update_agent, list_agents, get_agent Modifier les consignes ou les outils, lister, lire la carte des capacités code.push_sensitive pour les values, agent.create pour les droits ; read 2
    test_agent Envoyer un message de test et récupérer les étapes read (consomme le budget de l'agent) 2
    suspend_agent Couper un agent agent.suspend (nouvelle) 2

    Modifier deploy/ reste l'action code.push_sensitive d'aujourd'hui : refusée en sandbox, avec confirmation en demo, par PR en standard et critical. Un guide cnp-ai dans cnp-agent-kit (servi aussi par get_guide) explique à l'assistant comment enchaîner ces outils.

    Exemple dans Claude Code : « donne l'accès IA à mon app twitter-clone avec 50 000 tokens par jour ». L'assistant appelle get_project_ai, puis enable_app_ai. La CMP écrit le ProjectRecord et pousse le bloc ai dans les values de l'app. Argo CD déploie, et l'app reçoit ses variables.

    9. Le serveur MCP de la CMP face aux agents hébergés¶

    Deux changements sont nécessaires.

    Accepter les jetons des agents. Le serveur MCP de la CMP n'accepte aujourd'hui que ses propres jetons opaques, émis par son OAuth aux assistants (provider.load_access_token). Un agent hébergé arrive par la gateway avec un JWT Keycloak. Recommandation :

    1. Prérequis : vérifier l'audience sur l'API de la CMP (écart G7). decode_platform_token accepte aujourd'hui tout JWT du realm 3istor (verify_aud: False). Un jeton d'agent prévu pour la gateway serait donc accepté par l'API de la CMP. On ajoute une audience cmp-api aux jetons de la CMP et on la vérifie.
    2. Un jeton par destinataire. Le serveur MCP de la CMP a sa propre audience, cmp-mcp. Un agent qui a des outils de la CMP reçoit une client scope optionnelle cmp-tools, avec un mapper d'audience cmp-mcp. Il demande ce jeton à part (scope=cmp-tools), ou par token exchange avec audience=cmp-mcp quand il agit pour un utilisateur. Les jetons destinés à la gateway gardent l'audience ai-gateway. C'est la règle de la spécification MCP : un jeton est lié au serveur qui le reçoit, et on ne fait pas suivre un jeton émis pour un autre.
    3. La gateway vérifie sans transformer. Sur la route /mcp de la CMP, agentgateway vérifie le JWT (émetteur, aud = cmp-mcp, filtre d'outils), puis le transmet tel quel. La CMP le vérifie à nouveau, comme elle le fait déjà pour les autres jetons.
    4. Ce que la CMP en déduit. azp désigne l'agent : il doit figurer dans spec.agents[] de son projet avec le statut active. Si sub est un utilisateur (token exchange), les droits sont l'intersection des droits de l'utilisateur sur le projet et des outils autorisés de l'agent. Sinon, l'agent agit avec son seul rôle d'agent dans son projet. Le journal enregistre via: <azp>.
    5. Couper. Suspendre l'agent désactive son client Keycloak et passe son statut à suspended : la CMP refuse ses jetons immédiatement, sans attendre les 5 minutes.

    Ce choix n'ajoute aucun composant, réutilise la vérification JWT déjà présente dans la CMP et ferme G7 au passage.

    Adapter la stake policy. Pour un assistant, ask veut dire « demander à l'utilisateur dans la conversation ». Un agent hébergé n'a souvent personne dans la conversation : ask devient alors confirm, une approbation dans la CMP. Le journal enregistre l'agent comme via.
