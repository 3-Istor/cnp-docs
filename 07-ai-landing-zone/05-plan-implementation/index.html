    Plan d'implémentation¶

    Statut : v1.0 du 2026-10-25, validée par Brian. Cette page sert de consignes à l'agent qui implémente (par exemple Claude Sonnet). Elle découpe les phases 0 et 1 en tâches ; les phases 2 et 3 seront découpées par une passe de spec à leur entrée, pas par l'agent d'implémentation.

    1. Règles pour l'agent d'implémentation¶

    Ordre de priorité des documents. 02-spec.md prime, puis 04-cmp-agents.md et 06-finops-ia.md, puis 03-phases.md, puis cette page. Une contradiction entre eux est une raison de s'arrêter, pas de choisir.

    Ce que l'agent décide seul. Le détail d'implémentation à l'intérieur d'une tâche : noms de variables, structure du code, tests, valeurs de requests et limits dans le budget mémoire, formulation des messages.

    Quand l'agent s'arrête et remonte le problème. Dans chacun de ces cas, il ouvre la PR en brouillon avec une section « Écart » qui décrit le problème, les options et sa recommandation, puis il attend :

    1. une décision de la spec est impossible à appliquer telle quelle (fonction absente, version incompatible, ressource qui n'existe pas) ;
    2. une vérification V échoue encore après deux tentatives de correction ;
    3. il faudrait un composant, un dépôt ou un service qui n'est pas dans la spec ;
    4. une modification affaiblirait une protection (ouvrir un egress, monter un secret dans un agent, désactiver une policy, élargir un scope) ;
    5. le budget mémoire de la zone IA (environ 4 Go) serait dépassé ;
    6. une action toucherait des données d'un tenant ou la branche main d'un dépôt.

    Règles de travail.

    • Une tâche = une branche et une PR par dépôt concerné, au format Conventional Commits, avec les sorties des vérifications V de la tâche dans la description.
    • Versions exactes partout (charts, images, CRD). Chaque version choisie est consignée dans le tableau §4 de cette page dans la même PR.
    • Aucun secret dans Git : Vault, puis le vault-secrets-operator déjà en place.
    • Tout passe par Git et Argo CD ou kustomize, comme le reste de la plateforme ; pas de kubectl apply à la main sur le cluster principal, sauf pour les vérifications.
    • D'abord un cluster k3d local, puis le cluster principal (D28).
    • Chaque brique : mesurer sa mémoire et la consigner dans la spec §7.

    6. Prompt de lancement¶

    À donner tel quel à l'agent d'implémentation, une fois ses accès prêts.

    Tu implémentes la landing zone IA de CNP. La spec est dans le dépôt 3-Istor/cnp-docs, dossier
docs/07-ai-landing-zone/ : lis dans l'ordre 02-spec.md, 05-plan-implementation.md,
03-phases.md, 07-flux.md, puis 04-cmp-agents.md et 06-finops-ia.md pour les tâches qui les
citent. La spec est validée : tu appliques ses décisions telles quelles.

Commence par la phase 0, tâche T0.1 (état des lieux sur le cluster), puis T0.2 à T0.5, puis
la phase 1 dans l'ordre du §3 de 05-plan-implementation.md.

Règles (05-plan-implementation.md §1) : une tâche = une branche et une PR par dépôt, au format
Conventional Commits, avec les sorties des vérifications V dans la description ; versions
exactes, consignées au §4 ; aucun secret dans Git ; d'abord un cluster k3d local, puis le
cluster principal ; tu ne fusionnes jamais toi-même, c'est Brian qui fusionne.

Arrête-toi et remonte le problème dans une PR en brouillon (section « Écart » : problème,
options, recommandation) dans les six cas du §1 : décision inapplicable, vérification qui
échoue deux fois, composant non prévu, protection affaiblie, budget mémoire dépassé, action
sur des données de tenant ou sur main.

Les clés Gemini sont déjà dans Vault sous kvv2/platform/ai/gemini/<n> : ne les lis jamais en
clair. Les vérifications qui dépendent du serveur GPU (V1.10 à V1.12, V1.15, T1.14)
attendent qu'il réponde au contrat du §5 de la spec.

À la fin de chaque phase, écris le rapport de phase (T1.11 pour la phase 1) et attends la
validation de Brian avant la phase suivante.
